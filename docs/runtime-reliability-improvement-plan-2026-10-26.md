# NEUMA 运行可靠性五项改进实施计划

日期：2026-10-26。状态：已实施；最终验证记录见 [实施记录](runtime-reliability-implementation-2026-10-26.md)。本文保留设计依据，实际模块、快照方案与兼容范围以实施记录和现行架构为准。

NEUMA 保留现有的需求澄清、架构设计、独立评审、研发验收和交付流程。本计划改善五件事：刷新后继续查看任务，重现已经发生的失败，集中维护公共执行规则，中断后分清是否已经执行，以及减少业务代码对 Pi SDK 的直接依赖。

最先建立小规模失败回放，再稳定 NEUMA 自有运行接口，随后逐步接入公共执行规则、执行结果核实和断线续看。每次迁移一个调用域，使用迁移前的回放与领域测试检查行为。完整实施不以更换 SDK、引入 Cordis、重组为大型多包仓库为前提。

## 1 五项工作与用户收益

| 编号 | 用户能感受到的变化 | 当前已有基础 | 本次需要补齐的部分 |
| --- | --- | --- | --- |
| 一 | 刷新或重新打开页面后，仍能查看同一任务的进度和结果 | 群任务与普通页面应用任务已有后台执行和持久记录；群事件已有顺序续读 | 将提交与查看分开，优先补齐主对话、架构构建和研发的请求绑定路径，统一续看规则 |
| 二 | 同一种错误更容易修好，修改后可以检查是否再次出现 | 已有脱敏失败模式、回环模型服务、恢复及协议测试 | 跨控制器复用的会话回放、严格脚本消费、故障注入及真实进程崩溃测试 |
| 三 | 各环节处理失败、取消和额度时更一致 | 已有预算持久化、调度器、会话绑定、原子存储与关闭流程 | 集中公共执行顺序和资源清理，各领域保留自己的业务策略 |
| 四 | 中断后能判断可以重试，还是需要先确认外部结果 | 工作流已有 running 先保存、非幂等中断进入 needs_review、不自动重放 | 将分派事实与结果分类贯穿受管操作、HTTP、MCP 和模型工具 |
| 五 | 升级底层模型运行程序时，减少对需求、设计和研发流程的影响 | 已有 PiSessionPort，前端已经只消费 NEUMA 协议 | 自有事件和能力契约、历史读取与文件工具适配、业务层依赖门禁 |

“后台继续”仅指 NEUMA 后端进程仍在运行时。退出后端、关机或进程崩溃后，应显示中断状态，并按原有条件继续；不能为了实现页面重连而自动恢复模型请求、外部动作或预算。

### 2.2 保留的业务规则

1. 预算与授权仍在实际调用前持久保存。刷新、重连、重新订阅、进程重启和适配器更换均不补发额度或授权。
2. 架构节点和全局预算、研发角色预算、群任务批量预留分别保留。公共代码不得简化为“每个网络请求统一扣一次”。
3. 业务状态、正式提交、独立评审、交付激活和恢复条件仍由领域控制器及原验证器决定。模型回复和运行事件不能直接授予通过状态。
4. 原 Agent ID、对话、候选、交付、代码快照和原生会话绑定保持有效。缺失或错绑的会话不能用新会话静默替代。
5. 不补写历史版本、用量或授权，不将旧记录缺失的新字段解释为“尚未执行”。新协议必须有明确版本和读取分支。
6. 文件目录、链接检查、强制隔离、凭据隔离和联网策略继续生效。回放不得执行真实外部副作用，默认测试不得增加真实模型调用。
7. 页面连接关闭与用户明确停止分开处理。明确停止仍要取消实际执行及属于该任务的子工作；切页只释放当前订阅。

### 2.3 三类数据的职责

| 数据 | 谁负责 | 保存什么 |
| --- | --- | --- |
| 业务记录 | 原有主对话、架构、研发、群、应用和工作流 Store | 需求、预算、授权、检查点、正式结果及真实业务状态；继续作为权威来源 |
| NEUMA 运行事实 | Pi 适配器产生，领域运行代码消费 | 请求尝试、文本增量、工具执行和停止原因；需要重启后保留的部分由领域 Store 提交 |
| 查看与回放数据 | 查看层投影、测试回放器 | 查看层读取业务快照和已提交事件；回放器提供固定模型行为并核对真实业务结果 |

统一操作索引只负责寻找所属业务记录、执行代次和订阅位置。它不能再独立维护一套具有审批效力的“成功/失败”状态。持久进度与对应业务状态应在同一权威写入边界提交；需要跨记录关联时，明确提交顺序和恢复核对规则，不依赖两次写入总能同时成功。

瞬时文本增量不逐 token 同步写盘。只有已提交内容才能推进持久续读游标；未提交片段在重连后可以从快照重新同步。最终回复先持久保存，再发布完成消息。

## 3 实施顺序与阶段交付

五项工作的编号保持用户讨论顺序，实际开发按依赖分阶段进行。

| 阶段 | 对应工作 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| M0 基线与契约 | 全部 | 调用路径、状态归属、预算差异、当前测试和性能基线清单 | 每个目标流程有明确的持久接受点、取消所有者及验证入口 |
| M1 最小回放 | 二 | 使用现有接口的回放器、首批失败用例 | 代表性失败能在无外部模型调用下稳定重现，脚本多调少调均能检出 |
| M2 自有运行接口 | 五 | Pi 适配器实现自有契约，完成一个调用域迁移 | 同一回放在迁移前后业务结果、预算和恢复判断一致 |
| M3 公共执行机制 | 三 | 资源清理和模型准入顺序，按域迁移 | 保存失败阻止请求，重试与压缩按原规则记账，无清理遗漏 |
| M4 执行结果核实 | 四 | 分派尝试记录、未知结果处理、真实进程崩溃用例 | 已生效但未收到回执的外部动作在重启后不会被自动重发 |
| M5 主对话续看 | 一 | 主对话提交、查看、订阅和停止的完整切片 | 接受回执丢失、刷新、多窗口和重复提交不增加执行次数 |
| M6 构建研发与收口 | 一及其余各项 | 构建和研发接入、已有群和应用查看适配、依赖门禁和文档 | 所有约定范围验收通过，旧记录可读，既有业务规则保持有效 |

M1 先复用当前 SessionFactory 和回环模型服务，避免等待新接口才能开始保护现状。M2 稳定自有语义后，将回放器接到同一契约。M4 的初始设计在 M0 完成，具体接入可以与 M5 的界面工作并行，但涉及副作用的迁移必须先通过 M4 验收。

排期按阶段验收推进。M0 记录受影响测试耗时、实际迁移点和首个切片工作量后，再给出各阶段的人日估算；不以文件数量或未知模型响应时间承诺固定完成日期。

## 4 第一项 刷新后继续查看任务

### 4.1 目标与范围

用户提交任务后，可以刷新、切换会话或重新打开页面，查看同一任务的最新状态；只有明确停止才终止工作。首个完整切片选择主对话，随后接入架构构建和研发，最后统一群与应用的查看体验。

群任务已有独立 worker；普通页面应用任务已先持久创建再后台执行。应用在 heldLease 模式下借用对话或群任务的工作槽，仍应继承父任务取消信号。项目助手和独立需求接口本轮保留现有请求语义，不在第一批无差别改造。

### 4.2 实施步骤

1. 盘点一次执行的身份。明确主对话 mutationId、消息 ID、构建对象、研发记录、群任务和应用 taskId 如何定位一次操作；统一查看引用应包含业务类型、所属对象、执行代次和原业务引用。Agent ID 不能充当单次操作 ID。
2. 拆开主对话的接收与执行。参数、权限、输入和幂等核验通过后，在现有业务记录中原子保存已接受输入及操作引用，再允许后台执行。只有持久接受成功才返回接受回执。
3. 明确取消信号的交接。接受前仍由 HTTP 请求控制上传和校验；接受后由服务端执行实例持有取消信号。显式停止、删除、配置关闭和服务退出继续传播到真实执行器。不能只删除 HTTP close 监听而不建立新的所有者。
4. 提供提交、查询、订阅、停止四种职责分离的接口。具体路由在实现时登记；旧流式接口可通过等待同一次已接受操作的兼容层提供原结果，不能启动第二次执行。旧接口在切换前继续遵守已发布的取消语义。
5. 建立快照与增量切换规则。快照附带已提交游标，订阅按 after 读取后续事件，并在接入实时通知期间补齐竞态窗口。客户端按操作、代次和序号去重；订阅来源与操作不匹配时拒绝。
6. 处理游标异常。游标超前、保留范围不足或记录版本改变时，返回明确的重新读取快照指示；旧记录没有事件游标时仅展示实际快照，不伪造历史增量。
7. 分开瞬时流与持久事件。瞬时流用尝试编号及块序号识别连续性；缺块时重新同步。正式回复与临时显示只结算一次，重连不得重复拼接文本。
8. 更新桌面前端。切页只解绑订阅；重新打开后读取当前操作并续看。停止按钮发送精确操作及代次，避免旧窗口误停同一 Agent 的新任务。浏览器断线只显示连接中断，不把业务任务改成失败。
9. 将同样职责接入构建和研发。继续沿用原构建锁、阶段预算、原生会话、检查点和交付激活规则。读取或订阅不能调用 build、resume 或任何模型入口。
10. 为已有群和应用增加查看适配，复用原存储与调度。保持父子任务取消传播，不再包一层新的调度器或重复占用工作槽。

### 4.4 验收标准

- 接受已落盘但回执尚未发送时断开连接；原幂等编号重试返回原操作，实际模型和业务执行次数不增加。
- 同一编号提交不同输入被拒绝，不能覆盖原输入或创建隐式新任务。
- 流式输出期间刷新、切页和多窗口重连，已提交回复不丢失、不重复；未提交片段能正确重新同步。
- 快照生成与订阅之间发生新事件，客户端仍收到完整后续事实。
- 重复事件、旧订阅迟到、旧代次结果和异常游标不能污染当前界面。
- 停止与正式提交、交付激活发生竞态时，终态由现有控制器原子决定；迟到结果不能覆盖已取消或已失效对象。
- 删除 Agent、更新交付、修改群成员和服务退出均保留现有中断语义；父任务停止后 heldLease 子任务不继续占槽运行。
- 重启只恢复查看；未完成操作显示 interrupted 或所属领域的真实状态，不自动调用模型、不重放外部动作、不补额度。
- 前端只消费 NEUMA 自有协议；桌面端完成真实刷新、切页、停止和重新打开检查。

### 4.5 兼容与回退

按主对话、构建、研发逐域切换。历史消息和检查点不批量迁移。已接受后台任务的查看与停止能力必须保留至任务结束，不能通过前端切回旧实现让任务失去管理入口。服务重启后保留新操作记录，使用原恢复规则核对，不自动排队重跑。

## 5 第二项 失败会话录制与回放

### 5.1 目标与已有基础

为固定的模型行为提供可重复的测试过程，检查工具调用、正式提交、预算、恢复和最终状态。现有 [失败模式说明](../test/fixtures/architecture-recorded-failures.md) 已明确其夹具是脱敏最小模式，部分原始回复缺失；这些用例继续作为局部回归，不能改称完整原始转录。

### 5.2 第一版回放格式

每个场景包含以下信息，由带版本的读取器在测试入口校验。

| 部分 | 内容 |
| --- | --- |
| 来源 | synthetic、deidentified-pattern 或 sanitized-transcript；完整性、删改说明、适用 SDK 和协议版本 |
| 初始状态 | 合成需求、候选、角色、已有预算、原生会话绑定及检查点 |
| 模型脚本 | 分块文本、工具调用、原始参数、正常结束、截断、重试、超时、断线或取消 |
| 请求匹配 | 角色、阶段、顺序、获准工具 schema、必要输入与上下文绑定 |
| 期望结果 | 请求与工具次数、正式提交结果、业务状态、预算变化、持久化产物 |
| 故障控制 | 属于测试进程的注入点、触发依据、清理要求；不成为生产绕过开关 |

先复用 [http-model.mts](../test/helpers/http-model.mts) 和真实控制器。涉及 SDK 映射时通过真实 Pi 及回环模型服务运行；只测试上层业务分支时允许注入自有运行接口的替身，避免所有测试都支付同样的启动成本。

### 5.3 实施步骤

1. 拟新增 `test/helpers/session-replay.mts` 与 `test/fixtures/session-replay/`，将模型脚本匹配和消费计数集中实现，保留现有专属断言。
2. 先在合成测试运行中生成记录，不扫描 `.neuma` 或读取用户历史。源代码测试和夹具都必须在隔离临时根目录运行。
3. 将以下五条代表链路纳入第一批：合法普通回复未正式提交；工具参数失败后局部修正并提交；最后一轮结果已保存但尚未消费时中断；开发与独立评审分别恢复；外部动作响应丢失后进入待核实。
4. 每次匹配角色、阶段、工具与关键上下文。多调用、少调用、串角色和未消费脚本均使测试失败，防止“少做了工作反而快照通过”。
5. 只归一化时间、随机 ID 和临时根路径等必要非确定字段。保留预算、权限、错误类别、正式提交和验收结论的真实差异。
6. 对回放输入保留来源版本、投影规则和必要的合成原文。压缩或请求时投影后的模型视图必须可在该夹具内重建；缺失正文的历史案例继续标记不完整，不能用当前内容补成精确历史。
7. M2 接口稳定后，让回放消费同一 NEUMA 请求与事件语义，停止建立另一套只供测试使用的生产状态定义。
8. 如后续需要引入用户选择的私有失败，另做明确的本地导出流程：只导出选中案例，经删改审核后才能进入测试库。原历史保持原样，不自动收集、不外传。

### 5.4 记录与脱敏规则

默认生产诊断保留必要身份绑定、阶段、次数、协议版本、错误码和分派阶段，不默认新增完整提示词、业务参数、工具结果或模型思考正文采集。

进入仓库的夹具采用字段白名单，排除认证头、Cookie、凭据及其引用、原始请求头、完整 URL 查询、私人文件路径、图片原始数据和模型思考字段。未知对象不能原样复制。业务正文使用合成内容或经审核的删改内容；替换身份与路径时保持案例内部一致，并重新计算夹具摘要。

脱敏丢失关键行为时，保存为失败模式并补充合成重现。不能将脱敏后的近似结果描述为未经修改的真实会话。

### 5.5 真实进程崩溃验证

拟新增 `test/helpers/recovery-child.mts` 及对应 integration 测试。父进程持有临时目录和外部测试服务，启动编译后的真实子进程。使用双向 IPC 门控：子进程在目标持久化完成后发送 ready，并暂停在正文执行或业务推进前；父进程收到确认后再 SIGKILL，避免依靠 sleep 或单向通知猜测时机。门控通过现有可注入存储或执行端口在测试进程实现，不向生产代码加入专用崩溃开关；SIGKILL 后从相同临时目录启动新进程恢复。

| 故障点 | 必须检查的结果 |
| --- | --- |
| 预算保存后、模型请求前 | 预算不清零；按现有规则核对剩余额度，不补回未知消耗 |
| 分派标记保存后、工具正文前 | 没有持久结果时按保守规则核实，不能凭“计划在正文前杀进程”推断生产环境必然未执行 |
| 外部测试服务已记下副作用、结果保存前 | 恢复不自动重发，服务端计数保持一次，显示结果待核实 |
| 结果保存后、业务推进前 | 消费原有效结果，不重做已完成调用；正式阶段提交或 pendingResult 恢复不重调原角色，普通工具结果后的必要模型续轮仍按原预算执行 |
| 保存失败或保存期间取消 | 保存失败阻止后续执行；取消后不进入工具正文 |

所有子进程测试必须有有界等待、终止回收、端口释放和临时目录清理。进程退出和恢复后都检查外部调用次数、磁盘记录与预算，不能只检查一个状态字符串。

### 5.6 验收与证明范围

- 首批五类用例可离线稳定运行；无真实 API Key 时仍能覆盖协议、预算和恢复行为。
- 对脚本顺序、角色或调用次数故意作出错误变更时，回放能检出，且失败信息能指出不匹配的阶段。
- 日志、失败输出和仓库夹具均不包含凭据、思考正文或原用户材料。
- 回放纳入现有 integration 登记；局部纯格式校验可登记 unit，不新增重复测试。
- 离线回放不证明当前真实模型会正确理解任务或选对工具。真实模型评估如有需要，使用独立合成任务、独立额度和明确运行入口，不混入默认测试，也不替代正式业务验收。

## 6 第三项 公共执行规则集中维护

### 6.1 集中的范围

集中执行顺序、事件解释和资源释放，保留业务选择权。

| 可提取的公共机制 | 继续属于领域控制器的内容 |
| --- | --- |
| 取消检查、请求准入、持久化成功后放行 | 角色额度、架构修复授权、返需、独立评审、交付条件 |
| 逻辑请求与网络尝试的关联、结构化失败 | 架构节点及全局账、研发角色预算、群任务预留与结算 |
| 文本和工具进度的 NEUMA 事件转换 | designing、evaluating、研发五阶段、群认领及整合等业务状态 |
| 注册资源并幂等释放、继续清理其他资源 | 可复用会话和共享服务的所有者、临时或永久关闭次序 |
| 已有原子存储和会话绑定传递 | 各领域记录 schema、历史兼容、哈希核验和恢复资格 |

### 6.2 实施步骤

1. M0 列出各领域现有准入与扣账位置。特别区分 beforeModelRequest 每个 HTTP 尝试的检查，以及 onModelCall 处的逻辑调用记账，不能将两者合并为一个请求计数。
2. 先提取资源清理。候选模块为拟新增 `src/runtime/execution-lifecycle.mts`：只登记本次执行实际拥有的监听器、取消回调、会话及租约；按既定次序释放，重复关闭无副作用。某项失败仍尝试其余清理，保留原任务失败和清理错误。
3. 先迁一次性会话，再迁研发会话，最后处理长期工作会话和群协作。任务结束只释放本次拥有的资源，不能关闭跨轮复用会话、共享连接或其他任务仍在使用的服务。
4. 提取模型准入顺序。候选模块为拟新增 `src/runtime/model-admission.mts`：调用领域检查与保存回调，确认保存成功，再检查取消和当前绑定，最后放行请求。公共代码不自行读写领域预算，也不选择新的默认额度。
5. 每迁一个领域，分别验证网络重试、工具后续请求、压缩、正常提交和取消。架构与研发的重试不重复扣逻辑轮次；压缩及群预留继续按各自原有账本处理。
6. 优先复用 [agent-scheduler.mts](../src/runtime/agent-scheduler.mts)、[model-limits.mts](../src/runtime/model-limits.mts) 和 [pi-session-state.mts](../src/runtime/pi-session-state.mts)。公共运行索引和查看层不得新增第二套工作槽或模型预算。
7. 最后核对检查点的外围重复。只有语义相同的串行化、原子性和绑定传递才提取；原 schema、恢复验证和权限条件继续留在原模块。

### 6.3 验收标准

- 准入保存失败时，真实回环模型请求数为零；取消在保存期间到达，也不会继续发出依赖请求。
- 同一组回放在迁移前后，模型与工具顺序、业务结果、逻辑额度、重试记录和恢复结论一致。
- 重复取消和关闭只释放一次；任一资源释放失败后，其余资源仍被回收，清理失败可定位。
- 一项任务结束后没有残留监听器、计时器和工作槽；复用资源仍可被其合法所有者继续使用。
- 不新增没有业务必要的抽象层，不以减少行数或文件大小作为验收标准。

### 6.4 回退方式

逐领域切换公共机制，保留原领域回调和存储格式。某领域验证不通过时，停止该领域迁移并恢复原调用路径，已完成领域继续沿用通过验证的实现。回退代码不能撤销已经发生的扣账、授权消费或正式提交。

## 7 第四项 中断后核实执行结果

### 7.1 用户目标与现有基础

用户应看到“还没执行”“已完成”“明确失败”或“结果需要确认”的真实含义。工作流已有非幂等中断进入 needs_review 的规则，本项保留这条规则并补充分派事实，不单独为所有领域增加新的顶层业务状态。

### 7.2 最小尝试记录

拟新增 `src/runtime/execution-attempt.mts`，提供内部类型、记录读取校验和共用分类规则。建议包含尝试 ID、操作标识、Agent/会话/交付/步骤绑定、输入摘要、尝试序号、分派阶段、结果引用及失败原因。

记录模型请求是否发出、预算是否消费和业务副作用是否已知时，使用各自明确字段，不能共用一个 sent 布尔值。输入摘要只用于同一授权任务内的版本绑定，不能替代原输入校验，也不自动进入公开诊断或测试夹具。

每次真实执行指定唯一的尝试所有者。工作流、应用、连接适配器和模型工具通过关联引用传递同一尝试；各层不能各记一次并各自决定重试。

### 7.3 分类与恢复规则

| 已持久或可验证事实 | 结果解释 | 恢复行为 |
| --- | --- | --- |
| 参数、权限或绑定被拒绝，尚未分派 | 未执行 | 修正并重新通过原准入条件后，才可建立下一次尝试 |
| 新协议没有分派标记，且执行被持久化屏障严格阻隔 | 未执行 | 可以按原策略决定是否重新执行；不得将此推理套用到旧记录 |
| 已有分派标记，但没有持久结果 | 结果未知 | 先核对；即使实际中断发生在工具正文前，也保守处理 |
| fetch 或 MCP 调用后超时、断线或无法解析结果 | 默认结果未知 | 有副作用动作不自动重发；保留真实异常原因 |
| 成功或明确结果已持久保存 | 结果已知 | 复用并消费该结果，不重复执行 |
| 服务提供可验证拒绝或查询证据 | 按已评审连接契约分类 | 保存证据来源；不能只凭通用 HTTP 状态码猜测是否产生副作用 |

取消说明停止请求已经发出，不证明外部服务尚未生效。执行结果和取消原因分别保存，界面可以显示“已停止，先核实上次操作结果”。

### 7.4 实施步骤

1. 为 [workflow-controller.mts](../src/services/workflow-controller.mts) 先完成一个尝试所有权闭环，复用已有 running/attempts 先保存规则；同步 [workflow-records.mts](../src/services/workflow-records.mts) 与 [service-port.mts](../src/services/service-port.mts) 的版本和读取校验。
2. 在参数、权限、版本和绑定验证通过后，真实工具正文前持久保存分派标记。保存失败即停止；保存完成后重新检查取消信号。
3. 工具返回结果后，先保存结果引用和已知分类，再回填模型或推进业务状态。保存失败时不发布成功；如果副作用可能已发生，恢复仍按未知结果处理。
4. 按工作流、受管操作、HTTP/MCP 连接、模型工具的顺序接入。只有覆盖了真实分派位置，才能将“没有分派标记”解释为未执行；SDK 的开始通知不能替代持久化屏障。
5. 结果未知时复用已有 needs_review 和继续入口。用户可提供经过核对的完成结果，或明确接受重试；两种选择都绑定当前任务、尝试和版本。
6. 只有原策略允许的只读或幂等操作可自动重试，继续核对预算。重试与上次逻辑操作保持稳定身份；是否向外部服务传幂等键由已评审契约决定，不能擅自添加请求头或 MCP 参数。
7. 对旧记录保留原保守读取路径。缺新字段不回填未执行，不自动重写旧历史，不因分类细化放宽现有恢复条件。

### 7.5 验收标准

- 分派保存失败时，父进程持有的外部测试服务调用次数为零。
- 外部服务已生效、回执丢失后发生真实进程崩溃，重启不自动重发，状态进入待核实。
- 成功结果保存后崩溃，恢复消费原结果，副作用调用次数仍为一次。
- 连续点击继续、刷新、控制器重建和重复回执不能创建新的隐式授权、补发预算或绕过核实。
- 非幂等、只读和幂等能力均来自可信设计与适配器约束，不信任模型自行声明安全。
- 既有 [service-workflows.test.mts](../test/services/service-workflows.test.mts) 和 [connections-protocols.test.mts](../test/services/connections-protocols.test.mts) 保持有效；新增测试覆盖独立分派与崩溃边界，不复制无关参数组合。

### 7.6 回退边界

先完成新版本读取和保守展示，再启用新写入。已产生新尝试记录后，回退版本必须仍能识别其格式和未知结果；不能删除分派记录、降级解释为未执行，或启用不理解该格式的旧执行路径。必要时将该执行域置为只读查看，等待兼容修复后继续。

## 8 第五项 NEUMA 自有运行接口

### 8.1 目标与耦合范围

业务控制器只依赖 NEUMA 自有的消息、工具、请求和恢复语义。Pi 继续作为第一个实现，SDK 特有类型、内部模块路径和原生历史处理留在适配边界内。

现有耦合不仅包含 pi-port 的事件类型，还包括架构和研发对原生历史的直接读取、ContextEvent 类型，以及研发文件工具工厂。实施不能只重命名一个接口文件。

### 8.2 契约内容

拟新增 `src/runtime/execution-port.mts`，按真实消费字段定义自有契约。最终名称和拆分以 M0 接口清单为准；以下名称不代表当前已存在的 API。

| 能力 | 必须表达的信息 |
| --- | --- |
| 创建与执行 | 角色、受控工具、上下文、输出额度、取消、执行结果 |
| 运行事件 | 文本增量、工具开始与结果、请求尝试、重试、压缩、停止和结构化失败 |
| 请求准入 | 逻辑请求与 HTTP 尝试的区别、是否实际发出、原有记账和请求前检查回调 |
| 用量与停止 | 实际返回的用量、截断、取消、空响应、无响应和不可用字段；未知不补零 |
| 会话保存与恢复 | 受限会话引用、绑定及格式信息、恢复结果；不公开 SDK manager |
| 只读历史 | 受限历史数据和来源证明，不产生写入、迁移、网络请求或恢复授权 |
| 工具与上下文 | NEUMA 工具 schema、原始输入校验、正式提交、图片能力及请求时投影 |

记账、原始参数核验和绑定恢复等必需能力在使用前明确检查；缺失能力时阻断相应操作，不能因为方法可选而静默跳过。业务状态、独立评审和交付审批不进入 SDK 适配器。

### 8.3 实施步骤

1. 根据现有控制器消费字段建立判别联合事件和自有消息类型。自有事件不得继续通过 Exclude 或继承上游事件集合获得定义。
2. 在 [pi-runtime.mts](../src/runtime/pi-runtime.mts) 和相邻适配模块中完成 Pi 到自有语义的转换，先保留旧导出作为过渡。按需将项目管理专属工具和提示词移回所属领域，避免适配器继续承担项目业务。
3. 保留每次 HTTP 尝试检查、逻辑调用记账、网络重试和压缩的区别。取消、截断和底层失败不能丢失原因，也不能从未知用量推算消耗。
4. 先迁主对话等较小调用面，再迁工作 Agent、架构、研发和独立复核；首个领域完成后必须跑 M1 回放，再扩大范围。
5. 收口历史访问。原只读历史的路径、符号链接、硬链接、UTF-8、树结构、bindingHash 和 sessionHash 校验由 Pi 适配能力保留，领域获取受限数据与来源证明。
6. 收口上下文和文件工具。迁移 [architecture-model-context.mts](../src/architecture/architecture-model-context.mts)、[development-context.mts](../src/development/development-context.mts)、[development-controller-types.mts](../src/development/development-controller-types.mts) 的 SDK 类型依赖；[development-file-tools.mts](../src/development/development-file-tools.mts) 保留 NEUMA 注入的安全文件操作，原生工具工厂仅留在适配层。
7. 使用同一套契约测试检查真实 Pi 适配器与业务测试替身。真实 Pi 通过回环模型服务验证映射，业务替身验证相同的上层义务。
8. 扩展 [hygiene-graph.mts](../scripts/hygiene-graph.mts)，明确允许导入 Pi 的适配文件和纯模型能力配置位置，禁止业务控制器重新导入 SDK 或直接打开原生会话。过渡例外逐项登记，在迁移结束后移除。

### 8.4 历史兼容与验收

Pi 适配器按原规则打开旧原生会话及受限文件引用；预算、授权和业务检查点仍由原领域 Store 与验证器读取、核验。新记录若需要适配器标识，只对新版本显式保存；不改写旧检查点，不跨适配器自动迁移会话，也不自动更换模型。

- 文本、工具结果、正式提交、取消、截断、重试和压缩的映射保持完整顺序和必要信息。
- 准入或扣账保存失败时没有真实模型请求，取消后迟到工具不能继续执行。
- 原生会话缺失、损坏或绑定不符继续拒绝，不自动新建替代会话。
- 独立评审不继承开发历史；只读核验不写入会话，也不触发模型调用。
- 文件工具保留原目录授权、链接拒绝、原子写入和隔离要求。
- 迁移前后，同一合成请求轨迹产生相同业务状态、预算、授权消费和恢复判定。
- 约定迁移范围内的业务控制器不再消费 Pi 原生事件或 manager；第二种运行器的实现不属于本轮完成条件。

提交或推送前执行 npm test 全量回归。页面验收优先使用 Codex 内置浏览器，围绕实际桌面端检查；外部浏览器测试只在确有需要且显式启用时执行。若影响包内容，再执行现有 package:pack、test:package:smoke 和 test:package:install。

回放与真实进程中断用例已接入现有 unit/integration 登记，未增加 test:replay 或 test:crash 包命令。可在构建后使用实施记录中的 node --test 定向入口。

### 9.2 验收矩阵

| 场景 | 最直接的验证层 | 关键证据 |
| --- | --- | --- |
| 回放脚本少调、多调、串角色 | 回放器单元及控制器集成 | 匹配失败定位、消费计数、真实业务结果 |
| 扣账保存失败与取消竞态 | 回环模型集成 | 网络请求计数为零、磁盘预算不被重置 |
| 重试与压缩 | 真实 SDK 回环集成 | 逻辑预算、HTTP 尝试及压缩记录分别符合领域规则 |
| 工具执行中硬中断 | 真实子进程与父进程外部服务 | SIGKILL 后磁盘事实、服务端副作用次数、恢复判定 |
| 页面刷新与订阅竞态 | HTTP 集成及桌面浏览器 | 同一操作 ID、连续游标、无重复执行、无旧结果覆盖 |
| 关闭与资源回收 | 生命周期集成 | 无残留槽位、进程、监听器和未结算会话 |
| 历史与权限 | 领域恢复和适配器契约测试 | 旧数据按原规则可读、错误绑定拒绝、权限未扩大 |

M0 在现有合法记录容量内建立短、中和接近上限的合成样本，记录快照读取、事件补齐、内存和界面恢复耗时。客户端数据折叠与浏览器渲染分别测量，再冻结可重复的回归门槛；不照搬 DS Harness 的基准数字作为 NEUMA 性能承诺。
